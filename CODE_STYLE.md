# Code style и правила декомпозиции

## 1. Статус документа

Этот документ фиксирует согласованный подход к реализации локальной версии сайта Snapbuild.

Он определяет:

- форматирование и именование;
- архитектурные границы;
- порядок построения UI от shadcn/ui до страницы;
- правила декомпозиции компонентов;
- работу со стилями, графикой и анимациями;
- минимальные требования к качеству.

Если реализация требует отступить от этих правил, сначала обсуждаем и документируем причину,
затем меняем код.

## 2. Технологическая основа

- React 19.
- Vite.
- TypeScript в строгом режиме.
- Yarn как единственный пакетный менеджер.
- shadcn/ui как source-owned основа UI-компонентов.
- Radix UI как низкоуровневая основа интерактивных примитивов shadcn/ui.
- Tailwind CSS для токенизированных утилитарных стилей и адаптивного layout.
- CSS Modules для сложной локальной стилизации, графики и анимаций.

В репозитории должен присутствовать `yarn.lock`. Команды других пакетных менеджеров в
документации и скриптах не используются.

## 3. Форматирование

- Кодировка UTF-8.
- Переносы строк LF.
- Отступ — 2 пробела.
- Максимальная рекомендуемая длина строки — 100 символов.
- Двойные кавычки.
- Точки с запятой обязательны.
- Trailing comma используется в многострочных конструкциях.
- Форматирование выполняет Prettier.
- Импорты и Tailwind-классы сортируются автоматически.
- ESLint запускается без допустимых warnings.

Форматирование не обсуждается в ревью вручную: его обеспечивают инструменты проекта.

## 4. Именование

### 4.1. Директории и обычные файлы

Директории и файлы, не представляющие React-компонент, именуются в `camelCase`:

```text
heroSection/
motionConfig.ts
sectionData.ts
useReducedMotion.ts
```

### 4.2. Компоненты

Файл React-компонента, его типы, стили, тесты и stories используют имя компонента в
`PascalCase`:

```text
sectionHeading/
  SectionHeading.tsx
  SectionHeading.types.ts
  SectionHeading.module.css
  SectionHeading.test.tsx
  SectionHeading.stories.tsx
  index.ts
```

Суффикс `.component` не используется.

### 4.3. Идентификаторы

- Компоненты и типы — `PascalCase`.
- Функции, переменные и хуки — `camelCase`.
- Хуки начинаются с `use`.
- Булевы значения начинаются с `is`, `has`, `can` или `should`.
- `UPPER_SNAKE_CASE` используется только для настоящих модульных констант.
- Интерфейсы и типы не получают префикс `I` или `T`.
- Обработчики внутри компонента именуются `handleAction`.
- Callback-пропсы именуются `onAction`.

## 5. TypeScript

- Включён strict mode.
- Предпочитаем `type`. `interface` используется только когда действительно требуется
  declaration merging или расширение публичного контракта.
- Типы импортируются через `import type`.
- `any`, двойные приведения и директивы подавления TypeScript запрещены без отдельно
  зафиксированной причины.
- Типы выводятся из единственного источника истины, а не дублируются вручную.
- Props нетривиального компонента выносятся в `ComponentName.types.ts`.
- Короткий внутренний тип допустимо оставить рядом с реализацией, если он не является частью
  внешнего контракта.
- Promise должен быть `await`-нут, возвращён или явно помечен через `void`.
- Ошибки не проглатываются пустым `catch`.
- Вложенные тернарные операторы запрещены.

`React.FC` не используется. Props передаются обычным типизированным параметром функции.

## 6. Экспорты и импорты

- Используются named exports.
- Default export разрешён только там, где его требует инфраструктура или фреймворк.
- Каждый архитектурный срез предоставляет публичный API через `index.ts`.
- Межслойные импорты выполняются через публичный API среза.
- Deep imports в чужой срез запрещены.
- Циклические зависимости запрещены.
- Низлежащий слой не импортирует вышележащий.

Разрешённое направление зависимостей:

```text
app -> pages -> widgets -> features -> entities -> shared
```

Слой можно пропустить, если он не добавляет самостоятельного смысла.

## 7. Архитектурная спираль UI

Используем облегчённое слоение FSD и наращиваем компоненты от технических примитивов к
странице:

```text
shadcn primitive
  -> brand primitive
    -> entity
      -> feature
        -> widget
          -> page
```

### 7.1. `shared/ui/primitives`

Source-owned компоненты shadcn/ui:

- `Button`;
- `Card`;
- `Tabs`;
- `Sheet`;
- `Dialog`;
- `Accordion`;
- `ScrollArea`;
- `Separator`;
- `Tooltip`;
- формы и поля ввода.

Правила слоя:

- не знает о Snapbuild, секциях страницы и контентных сущностях;
- содержит базовые доступные состояния;
- использует CSS-переменные дизайн-системы;
- варианты оформляет через CVA;
- прямой импорт Radix UI разрешён только здесь;
- исходник shadcn/ui можно изменять: это принадлежащий проекту код;
- примитив не оборачивается ещё одним компонентом без нового семантического контракта.

### 7.2. `shared/ui/brand`

Фирменные, но всё ещё предметно-независимые композиции:

- `SectionHeading`;
- `Surface`;
- `MediaFrame`;
- `IconButton`;
- `GradientPanel`;
- `ResponsiveContainer`.

Они собираются из shadcn-примитивов и токенов проекта. Brand-компонент появляется, только
если задаёт повторяемую визуальную роль или устойчивый API.

### 7.3. `entities`

Повторяемые смысловые единицы контента:

- карточка возможности;
- элемент roadmap;
- security-карточка;
- строка сравнения;
- отзыв пользователя.

Entity знает смысл своих данных, но не знает, на какой странице, в какой секции и колонке она
используется.

### 7.4. `features`

Законченные пользовательские взаимодействия:

- мобильная навигация;
- FAQ accordion;
- интерактивная демонстрация продукта;
- carousel или slider;
- lightbox;
- сценарий формы.

Feature владеет своим состоянием и поведением, но не определяет layout всей страницы.

### 7.5. `widgets`

Самостоятельные секции страницы:

- `Header`;
- `HeroSection`;
- `WorkflowSection`;
- `UseCasesSection`;
- `RoadmapSection`;
- `SecuritySection`;
- `FaqSection`;
- `Footer`.

Widget соединяет примитивы, entities и features, владеет внутренним layout секции и может быть
показан отдельно в Storybook.

### 7.6. `pages`

Страница:

- задаёт порядок widgets;
- задаёт page-level layout;
- передаёт данные и связывает сценарии;
- не содержит подробную разметку карточек и интерактивных элементов;
- не дублирует логику нижележащих слоёв.

### 7.7. `app`

Содержит bootstrap приложения, провайдеры, глобальные стили, настройку темы и маршрутизацию.

## 8. Когда выделять компонент

Компонент выделяется, если у фрагмента появляется хотя бы одна самостоятельная причина для
изменения:

- отдельная семантическая задача;
- собственный визуальный контракт;
- собственное интерактивное состояние;
- повторяемая структура;
- возможность независимо показать или протестировать;
- сложная графика или анимационный сценарий;
- нетривиальный адаптивный layout.

Количество строк само по себе не является критерием.

Не создаём компонент:

- ради переименования одного `div`;
- ради единственного набора классов без семантического контракта;
- заранее, на основании гипотетического повторного использования;
- если обёртка полностью повторяет API нижележащего примитива.

Локальный компонент остаётся внутри widget или feature, пока не появится реальное повторное
использование или более широкий смысл.

## 9. Ответственность за layout

- Внешние отступы компонента задаёт родитель.
- Компонент не задаёт себе постоянный внешний `margin`.
- Внутренние `padding` и `gap` принадлежат самому компоненту.
- Page определяет расстояния между widgets.
- Widget определяет расстояния между своими внутренними блоками.
- Entity не делает предположений о номере колонки или позиции в списке.
- Карточка не меняет layout на основании своего индекса в массиве.
- Контейнер не навязывает вертикальный ритм контенту без явного контракта.

## 10. Стили и дизайн-токены

- Цвета, типографика, размеры, радиусы, тени, blur, duration и easing задаются токенами.
- Для одного визуального параметра существует один источник истины.
- Используются семантические имена: `primary`, `surface`, `muted`, `danger`, а не название
  конкретного цвета.
- Повторяющаяся визуальная роль становится вариантом CVA или отдельным brand-компонентом.
- Произвольные значения Tailwind допустимы только для точного воспроизведения референса и
  после проверки, что значение не является общим токеном.
- Порядок Tailwind-классов поддерживается автоматическим formatter plugin.
- CSS Modules применяются для сложных селекторов, псевдоэлементов, масок, декоративной
  графики и keyframes.

Inline styles следует избегать полностью. Они допустимы только как крайнее исключение, если
значение вычисляется во время выполнения и его нельзя корректно передать через класс,
`data-*`-атрибут или CSS custom property. Даже в таком случае сначала передаём динамическое
значение в CSS-переменную, а визуальное правило оставляем в stylesheet.

## 11. Графика

- Интерфейсные иконки берутся из согласованного icon set.
- Случайные символы Unicode не используются вместо иконок.
- Точная векторная графика реализуется через SVG.
- Сложная декоративная композиция изолируется в собственном компоненте.
- SVG должен иметь корректную доступность: декоративный скрывается от accessibility tree,
  смысловой получает доступное имя.
- Изображения получают корректные размеры и не вызывают layout shift.
- Контентные изображения имеют осмысленный `alt`; декоративные — пустой `alt`.

## 12. Анимации

- Анимация объясняет изменение состояния или поддерживает визуальную иерархию.
- Простые hover, focus и press transitions реализуются CSS.
- Координированные последовательности и анимации, зависящие от React-состояния, изолируются
  в отдельном сценарии или компоненте.
- Duration и easing берутся из токенов.
- Поддерживается `prefers-reduced-motion`.
- Анимация не должна блокировать взаимодействие.
- Появление контента не вызывает layout shift.
- Начальное, активное, конечное и прерванное состояния должны быть определены явно.
- Повторяющиеся scroll-анимации используют общий механизм, а не набор разрозненных effects.

## 13. React и состояние

- Производные значения не хранятся в state.
- `useEffect` используется только для синхронизации с внешней системой.
- Локальное UI-состояние располагается максимально близко к владельцу сценария.
- Состояние не поднимается выше без реальной необходимости.
- Не используем сериализованный `key` для принудительного remount компонента.
- Не используем глобальный store для локальной анимации, accordion или меню.
- Event listeners, observers и timers всегда очищаются.
- Семантический HTML предпочитается абстрактным `div` и `span`.
- Keyboard navigation и `focus-visible` считаются частью базового UI-контракта.

## 14. Контент и данные

- Повторяемый контент отделяется от JSX в типизированные структуры.
- Компонент не выбирает текст по случайным индексам или CSS-селекторам.
- UI получает минимальный view model, необходимый для отображения.
- Технические данные и детали источника не протекают в примитивы.
- У списков есть стабильные предметные keys.
- Пустые, ошибочные, загрузочные и disabled-состояния проектируются явно там, где они
  применимы.

## 15. Storybook и тесты

Для публичного примитива, brand-компонента, entity и widget предусматриваются:

- `Default` story;
- все значимые визуальные варианты;
- интерактивные состояния;
- крайние варианты контента;
- мобильное и десктопное представление, если layout существенно отличается.

Тесты проверяют наблюдаемое поведение, а не внутреннюю реализацию:

- доступные роли и имена;
- keyboard interaction;
- изменение состояния;
- callbacks;
- граничные состояния.

Статичная разметка без поведения не покрывается тестом только ради процента coverage.

## 16. Проверка качества

Основная проверка выполняется одной Yarn-командой и последовательно запускает:

```text
format:check -> lint -> typecheck -> test -> build -> deadcode
```

Рекомендуемые команды:

```bash
yarn format:check
yarn lint
yarn typecheck
yarn test
yarn build
yarn deadcode
yarn check
```

Изменение считается готовым, когда:

- все проверки проходят;
- нет ESLint warnings;
- нет необъяснённых TypeScript suppressions;
- проверены ключевые viewport sizes;
- проверены hover, focus, active и reduced-motion состояния;
- визуальная реализация сопоставлена с референсом;
- публичные контракты и архитектурные границы не нарушены.

## 17. Приоритеты при спорном решении

В порядке убывания приоритета:

1. Точность воспроизведения поведения и визуала референса.
2. Доступность и корректная семантика.
3. Ясные архитектурные границы.
4. Предсказуемый и небольшой публичный API компонента.
5. Простота поддержки.
6. Повторное использование на основании реальных повторений.
7. Минимальное количество абстракций.

Если точность референса конфликтует с доступностью или корректностью поведения, решение
сначала обсуждается, а не принимается молча.
